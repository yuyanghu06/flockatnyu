# Planner throughput fixes

Goal: fix task-history save failures and repeated reads, then raise the production batch cap from two to five so the planner can process incoming work more efficiently.

Status: deployed and verified live. Independent evaluator ACCEPT covers the implementation, exact package, two-input gate and final five-input live gate. Production deployment `02cda8db-208b-4434-ad2c-a8365e93036c` is online with cap five. Its first ordinary run acknowledged all five inputs in 199.544 seconds, after successful final task saves. Follow-up still hit its round cap.

Scope: lossless compression of oversized execution history within the existing 256 KiB database limit; bounded pages for history or the complete saved task; transfer of current-cycle read results into follow-up; and a five-minute selection delay for unchanged older tasks that were actually inspected. Preserve originals, prior history, source permissions, exact versions, leases and expiry. No schema migration or silent truncation. Keep 16 initial rounds, 10 follow-up rounds, 64 tool calls per stage, the 600-second deadline and one-second Discord pacing.

Ownership: storage coder owns task-store.js and task-history-codec.js; pipeline coder owns staged-pipeline.js; primary owns handler.js, prompt.js and observation-handoff.js. Tester owns new storage, paging and model checks. Primary serializes documentation and release. Unrelated frontend and map edits are outside this release.

Acceptance: reproduce rejected saves using actual local PostgreSQL; recover every history field exactly; reject corrupt data and stale or unauthorized writes; reconstruct Unicode pages with exact versions; preserve compact action proof and unrelated tasks; demonstrate five-input handling and read reuse with the configured model, production runner and simulated sources; obtain independent acceptance; then deploy the isolated package and verify normal live runs at five inputs.

Verification: all 31 new checks pass on production Node 22.23.4. The broader set has 278 passes and exactly the same 10 failures as its baseline: one missing historical fixture and nine individually reviewed older contracts. The root API build and the packaged worker's 56 JavaScript syntax checks and entry imports pass. The web-only API check assumes files intentionally absent from the worker package and is not a worker gate.

Actual-model evaluation used gpt-6-luna for 40 of 48 permitted requests, all HTTP 200, with inference-only network and simulated business services. Five fresh inputs completed in eight requests, with zero equivalent repeated complete-source reads. Outage and concurrent-edit cases preserved unfinished work and human fields, but reached the follow-up round cap. All 40 recorded replies replayed offline through the exact isolated package with matching tool results, final fields and checkpoints; that replay made no new inference calls.

Release package: 62 reviewed files, with two unrelated map/diagnostic files restored only in the package to their prior deployed bytes. Private credential scan passed. Source commit `041b280`. Only the worker is in scope. Live configuration changed only AGENT_AUTOMATION_MAX_INPUTS from 2 to 5 after a normal run on the new image.

Limits and rollback: compression is bounded storage, not unlimited capacity. Incompressible or over-budget tasks fail explicitly and preserve prior state. Decoded history has a 16 MiB guard; the existing aggregate list guard is 54 MiB. The new reader supports legacy plain tasks. An old image cannot read newly compressed histories, so first reduce the cap to two on the same fixed image; any code rollback must retain the new decoder. Follow-up round caps and no-change source-review completion gaps remain separate open issues.

Private evidence: evidence/planner-throughput-fix-2026-10-25/ contains package hashes, local and Node 22 results, model evidence, offline replay, baseline comparison and live release receipts. It contains no credentials, system prompts or raw live source responses.

Live outcomes: the cap-two gate acknowledged two inputs in 119.377 seconds. The first cap-five run claimed five at 5:52:53 PM and acknowledged five at 5:56:11 PM New York; 31 calls and 22 successful model requests. No task-storage failure appears in either supplied gate window. No Discord source-tool calls were proposed during the five-input run's follow-up phase; one identical map-read proposal repeated. This supports reuse of initial results; actual permission checks and necessary refreshed map reads remain independent. Both completed runs hit the follow-up round cap. One retry hit its initial cap and another was interrupted by normal deployment shutdown and retained. One startup audit-retention cleanup failed in each new container. These outcomes do not establish sustained backlog draining or eliminate all unrelated completion failures.
