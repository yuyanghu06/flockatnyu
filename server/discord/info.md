# Discord live reads and metadata discovery

This folder supports read-only bot retrieval and channel/thread metadata discovery. Message content is fetched live; larger on-demand summaries run only in request memory with bounded evidence and original citations. No historical Discord message archive, durable summaries, vectors or accounting are stored. New native events may remain in the shared temporary pending queue until explicitly processed. Tools do not post messages or join private threads. Credentials remain private server settings.

`live-config.js`, `live-client.js` and `live-retrieval.js` enforce trusted source scope, content capability, enabled catalogue entries, current policy and fresh bot/parent metadata. Unknown or excluded channels and ambiguous ancestry fail closed. Results disclose coverage. Accepted descendant-thread search hits need their own allowed source UUID and ancestry beneath an originally selected channel; final policy/catalogue checks cover every accepted source. A failed/partial read has no stored-summary fallback.

The live summary adapter owns the request-memory summarization path. Its helpers pack bounded inputs, validate original citations and enforce request budgets. These helpers support user-requested live windows only; no periodic content/embedding job remains.

`store.js` supports protected channel configuration, policy and metadata discovery against `discord_view_policies`, the sole Discord table. Its JSONB catalogue retains stable source UUIDs, names/types, eligibility/access metadata and discovery generation/cursors. Discord sources do not duplicate `knowledge_sources`. `discovery.js` resumes bounded metadata pages and reconciles only complete generations; it never stores message bodies.

`cli.js` supports metadata preflight, registration, policy and discovery; explicit one-shot discovery uses `npm run discord:discover`; the redundant generic worker wrapper was removed. Railway now runs `event-cli.js serve` continuously as `discord-events`. Its shared queue holds native creates/edits/deletion payloads until handled; no historical backfill or content archive exists. Applied migrations remain immutable and are never run at startup.

The policy table forces RLS and remains service-only. Trusted chat and update-agent principals derive Discord source UUIDs from the current service-only published catalogue and inherited blacklist. Configured source grants continue to control non-Discord adapters; current bot/policy checks remain mandatory. HTTP administration still requires trusted admin context. No per-person membership tables or source grant expansion follows from collection.

## Event collector

`event-cli.js serve` runs the independently deployed collector. `event-config.js` reads its opt-in switch; `event-listener.js` applies current guild policy, inherited blacklists, bot access and source identity before enqueue. `gateway.js` uses the Gateway-only SDK for heartbeat/reconnect and serializes committed checkpoints; `event-state.js` accesses only metadata CAS RPCs. Shutdown uses a resumable close code. Invalid/expired Discord sessions are disclosed as possible gaps; historical message backfill is never started.

`live-summary-utils.js` holds pure UTF-8 chunking used by the request-memory summarizer. No archive or vector provider remains in production source. Metadata management remains in `cli.js`; hourly/event-triggered metadata refresh in the listener replaces the old daily Railway discovery job. Migration020 records explicit manual disables in existing channel JSONB so discovery cannot re-enable them.

## Chat routing and leadership privacy

`channel-scope.js` maps the verified eboard/team category IDs to default eboard, general fallback and explicit-request team scopes. Live chat reads receive only the current user's text; source text/history cannot authorize teams. The server-built Discord chat principal additionally permits implicit reads from its exact invoking team destination; a trusted transport marker and invoking channel ID are required, and thread parents/sibling teams receive no implicit opt-in. Website, named requests and stateless HTTP tools retain their existing team gates; negative/exclusion clauses cannot opt in. Automation retains its independent eligible source scope. Shared live policy excludes leadership-team and all descendants; defaults include its ID. Policy changes require a completed metadata-only discovery refresh before catalogue reads resume.

Shared request-pacing.js serializes bot metadata/content per process and bot/fetch transport, with default750ms spacing,429Retry-After/JSON/headercooldowns and proactive exhausted-bucket waits. Channel summary workers are sequential; request90s/scan120s bounds preserve truthful partials and existing access/content/cost caps. Independent service processes remain separately paced.

Metadata refresh continuation lives in metadata-refresh.js: coalesced refresh promises resume only the same current policy/generation after bounded slices. Three attempts use cancelable5second gaps; unfinished generations schedule another5second invocation, terminal failures60seconds and verified completion the normal hourly cadence. Startup resumes pending work; existing completeDiscovery remains the sole publisher of readable channels.

Observed revocations withdraw affected channels immediately, and completion alone grants new access. Initial/legacy incomplete generations and policy changes stay closed. Named-team when/where questions now authorize only a full distinctive team name; generic meeting/chat words and shared tokens cannot opt into unrelated teams. Exact scope=team summaries use the existing single-channel authorization path, including current user intent, published source scope and leadership exclusions.

Catalogue name queries normalize punctuation/separators and inspect ancestor names, so a natural team name resolves slugged channels and generic child channels. Metadata matching never grants access: current source, team intent, exclusions and final catalogue checks still run.

`chat-*` implements eboard/team mention/reply and thread conversations: current member/destination/source access, private service bridge, REST delivery and bounded RAM transport state. ACL-safe eboard sources may join a reply profile; team sources include only the own destination and necessary registered parent, never sibling teams based on equal ACLs. Profiles bind the trusted transport and exact invoking channel. Existing Gateway dispatches chat independently of ingestion checkpoint work. Self-generated create/update events do not enter autonomous input. Source blacklists and live-only retention remain authoritative. See `../../docs/discord-chat.md`.

`chat-context.js` loads the previous hour from the exact invoking channel/thread through authorized live-window reads and reads only Discord ID/display-name pairs from Supabase. Coverage is bounded and explicit, data stays request-local, and Discord chat enforces a 20-minute default/maximum overall deadline through `DISCORD_CHAT_TIMEOUT_MS` on web and discord-events. The collector adapter, web bridge and Discord shared-runner instance use that bound; private HTTP transport allows 30 additional seconds while preserving caller cancellation. Explicit shorter settings remain supported. Website and individual provider/source deadlines remain separate and unchanged. Full 20-minute requests require the web service Railway private origin with explicit port; public HTTPS remains supported but subject to Railway proxy limits. The remote bridge accepts HTTP only for strictly validated single-service `railway.internal` roots and uses native Node HTTP with request cancellation/deadline and the existing 250 KB response cap, without a separate fetch headers timeout. Shared-secret authorization remains mandatory. Both web and collector need updated source; old collector images reject the private HTTP origin and retain the earlier timeout cap. The web listener must accept Railway private IPv6 (`HOST=::`), and the origin port must match its actual `PORT`.

Discord chat uses all shared website assistant adapters through `createChatRunner`, including Google/Calendar, read-only Miro, map/attendance, memory and bug reports. Existing configuration/source/action/evidence gates remain. The principal's top-level UUID list combines configured shared sources with the current audience-approved published Discord UUIDs; a separate required `liveDiscord.allowedSourceIds` subset restricts Discord reads to the approved channel audience. Retrieval intersects both lists before catalogue access. Google access requires the website's `SITE_GOOGLE_ENABLED=true` grant, and both lists plus that grant bind the transient profile and final authorization check. Verified Discord labels do not establish linked roster identity or source evidence.

Automatic bot-ping reply context is fetched by the web service through fetchReplyContext using the approved actor ID and exact trigger ID. It rereads that original trigger, validates its direct same-channel/guild reply reference and fetches only that exact target, even if older than the previous hour. It never follows a reply chain or trusts embedded referenced_message payloads. Existing allowed-source/audience/channel/exclusion checks and post-read policy verification remain mandatory. The optional repliedMessage context contains whole text up to10000characters and only allowlisted author/time/identity/URL metadata; embeds remain unread, oversized text is explicitly withheld and failure is unavailable. Eligible image attachments are handled separately as described below. No reply bodies enter operational logs, audits or client metadata.

Discord source HTTP requests, catalogue storage, identity directory and automatic chat context use the shared 60-second default. Live retrieval falls back to 60 seconds when no runtime budget is configured. Existing explicit scan budgets (normally 120 seconds), 90-second pacing budget and caller cancellation still bound the work; pacing intervals and source authorization are unchanged.

`collector-diagnostics.js` emits content-free collector lifecycle diagnostics with fixed status/stage names, allowlisted error codes and bounded numeric HTTP/close/shard/queue fields. Checkpoint load/validation/save, Gateway construction/connect/SDK failures, event ingestion/metadata refresh and queue overflow are distinguishable. Known nested network failures may supply a causeCode; unknown errors stay unknown_error. SDK SocketError remains nonfatal. Logs never serialize error messages/stacks, source events, credentials, URLs, guild/channel/message IDs or session checkpoints. Startup emits diagnosticsVersion:1; shutdown records only fixed signal/failure reasons. Logging failures cannot prevent lifecycle cleanup. Executable-only uncaughtExceptionMonitor adds a safe summary without intercepting Node's default crash behavior; default Node stderr is not globally sanitized. Explicit parent cancellation does not produce a fatal failure or advance the interrupted checkpoint. Restart policy, checkpoint ordering and reconnect behavior are unchanged.


`chat-images.js` adds request-local PNG/JPEG/WebP vision to Discord chat. Only the trusted invoking Discord-chat transport opts into internal descriptors from `fetchReplyContext`/`fetchWindow`: the exact freshly actor-verified trigger, its validated same-channel/guild direct reply (including older replies), then newest accepted previous-hour messages. Ordinary live tool/source envelopes and automation never receive signed CDN descriptors. A failed trigger verification prevents all image use. Up to40candidate descriptors are scanned and attachment identities are deduplicated; the shared upload validator enforces four images,5MiB per image,10MiB total and MIME/signature agreement. A separate10MiB download budget charges every consumed stream chunk, including failed streams and rejected signatures; declared-size preflight and exhausted-budget omissions prevent failed candidates from multiplying I/O. Only exact HTTPS Discord CDN/media `/attachments/<channel>/<attachment>/<filename>` URLs bound to those originals are downloaded, with signed-query allowlisting, no credentials, redirects, bot authentication, arbitrary URLs or embed expansion. Header/stream/declared-size checks and a cancelable deadline bound I/O, including stalled fetches and bodies.

The loader rechecks current source policy/catalogue and fresh channel/thread ancestry after downloading; failure discards every image. The bridge additionally rebuilds the audience-bound authorization profile before any image model dispatch, then retains the existing final publication check. Image bytes return separately as `imageAttachments`, and the bridge validates them and clones only the final current user message to carry attachments through existing multimodal planning and answering. The user question is unchanged; remote collector requests still cannot submit uploads. Bytes and signed CDN URLs never enter system context, run metadata, audit inputs, transport history or stored source knowledge. Optional strict `imageContext` contains only canonical message citations, names/IDs, counts and fixed coverage outcomes. Both model phases treat image text/pixels/names as untrusted evidence without action, source-access or participant-identity authority. Text coverage and listed-image coverage remain separate; unsupported GIF/SVG, embeds, stickers, external image links and omitted/failed candidates are disclosed rather than inferred. Provider support remains the existing chat attachment capability.

`source-scope.js` resolves enabled same-guild UUIDs from fresh `getPolicy`/`listSyncChannels` results for authenticated local-operator principals. It grants nothing for paused/discovery-disabled policy, malformed/unavailable responses or capacity overflow; unrelated source grants survive failures. Website chat, tools and map routes enrich only backend-authenticated principals. Newly completed discoveries need no static UUID configuration. No principal/source-scope cache is retained; downstream live checks still enforce current blacklist, bot permissions, ancestry, team intent and transport audience. Migration035 alone publishes new catalogue grants.

Discord conversation admission is configured separately on the collector and private web bridge. The parser retains fallback3total/1permember, accepts total1–10 and member1–5, and production10/5 uses explicit variables on both services. Counters and histories remain process-local; overlapping requests for the same member/destination take independent history snapshots and the last successful completion replaces the RAM history.

Cross-channel message preparation uses the bridge-only adapter in `../../tools/discord/draft.js`, reusing current destination authorization for metadata and actor/bot eligibility. It prepares review text only: no target message reads, source-principal replacement, sends or persistent native drafts. Existing transport remains pinned to the invoking reply.

manual-scope.js is a trusted per-run facade over043selected-node/ancestor metadata and fresh live bot access. It overrides only channel/category exclusions for exact requested queued channels, preserves manual disables/pause/withdrawal/guild/identity checks and never edits published scope or ordinary chat/map visibility.

The facade's server-only `getAuthorizationSnapshot` supplies policy and channels
from one fresh validated snapshot for each authorization pair. Worker batch
authorization and live retrieval use it for their opening pair and call it again
independently for their final recheck. Ordinary stores retain separate policy and
catalogue reads. There is no persistent or in-flight snapshot cache; live metadata,
ancestors, permissions, source bindings and final withdrawal checks still run.

`metadata-reconcile.js` checks only a native channel/thread event's exact target and its ancestors through current REST permissions. Its service-only snapshot/publication RPCs preserve existing same-policy publication, source IDs and manual disables. Gateway metadata work and unknown-channel ingestion use this bounded path instead of waiting for archived-thread discovery. Relevant metadata changes fail the snapshot comparison rather than consuming an unresolved original. A changed catalogue fences older scans with `restartRequired`; the next full scanner restarts from the current catalogue, while complete archive promotion still requires every actual cursor. No message-history reads are added. Migration044 must be applied before deploying this collector; a collector predating restart support cannot resume flagged work.
