# Raw sender-cache enrichment worker

This separate opt-in service reads original contacts_cache senders, calls Treg with only an address and saves the native raw contact only in Contacts. Cache rows stay unchanged. Separate typed processing records hold leases, budgets, request IDs, retries and completion receipts; they never hold enrichment payloads.

worker.js controls ordered processing and truthful outcomes. config.js reads private settings. store.js binds the v2 probe/claim/renew/complete/defer RPCs; cli.js provides status/once/serve. Revised unapplied050 supplies atomic contact insertion plus processing completion after actual047/049. No collector, planner, Gmail provider or UI work occurs here. Root owns guides/journals; preserve others' files. Actual implementation/evidence/release status is in milestones/milestone.md.

schedule.js gates New York 09 and drains finite batches through the existing worker until empty, a safe limit/failure or cancellation. cli.js exposes scheduled/drain in addition to explicit development commands, closes resources and keeps output content-free. Production uses UTC13/14 with the local-time gate and exits between runs.

Each batch handles at most fifty sender inputs, one email at a time. GMAIL_ENRICHMENT_BATCH_SIZE defaults to fifty and accepts one through fifty; lower legacy item/request limits can further reduce a batch, while higher limits cannot bypass its fifty-input cap. Scheduled/drain runs may process several batches, with an abortable pause using the existing poll interval (five seconds by default) between successful nonempty batches. Empty, failed, budget-limited, uncertain-cost, logging-failed, cancelled or final permitted batches do not wait or start an extra batch. The existing money, lease and provider limits still apply within each batch; fifty is an upper bound, not a guarantee that spending permits fifty lookups.

treg.js is this service's fixed direct Tomba-first, Apollo-second client. It permits at most two provider calls per email (GMAIL_ENRICHMENT_MAX_PROVIDERS may reduce this to one), shares the existing per-email spending ceiling across both calls and stops on unknown costs or unsafe failures. Tomba uses GET with the email query; Apollo uses POST with the same query and no JSON body. Each attempt has its own private full-call log. A Tomba hit saves its complete native data person object unchanged, while the complete outer response remains in the private log; an Apollo hit saves its complete native response wrapper unchanged. A valid Apollo hit without a display name is still retained in Contacts. The website's separate Treg client and tools are unchanged.

The same daily-only module contains its credential and literal-email validation helpers. config.js uses that local credential reader, so the isolated service package does not include website Contacts/search modules or either shared website Treg client.
