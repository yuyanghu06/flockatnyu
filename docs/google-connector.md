# Railway Gmail and Drive connector

The assistant's Hono server calls Google's Gmail and Drive APIs through server-owned read tools. A cloud-hosted LLM never receives Google credentials. A local Codex/ChatGPT MCP connection does not automatically become available to a Railway process; these tools are the application's independent connector.

Implemented tools: `search_gmail`, `read_gmail`, `search_drive`, `list_drive_folder`, and `read_drive`. Gmail search hydrates subject/from/to/date/snippets, and reads extract bounded plaintext with inert HTML fallback, without attachments. Drive search returns names/descriptions/links; reads export Docs/Slides text, the **first sheet only** of Sheets as CSV, and small plaintext files. Unsupported binary files return metadata only. Search returns at most five results; reads are bounded and explicitly partial. These chat read tools expose no sending, modifications, Calendar writes or arbitrary URL fetching. The update agent has a separate fixed-target Calendar connector described below.

## One-time account setup

1. Choose a Google Cloud project and enable **Gmail API** and **Google Drive API**. Configure its OAuth consent screen for the intended account. A Workspace admin may need to approve access. External apps using Gmail/Drive restricted scopes can require Google verification; testing-mode refresh tokens may expire after seven days. See [Google's OAuth guide](https://developers.google.com/identity/protocols/oauth2/web-server).
2. Create a **Web application OAuth client**, registering exactly `http://127.0.0.1:8765/oauth2callback` as an authorized redirect URI.
3. Put `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_EXPECTED_ACCOUNT_EMAIL` in the ignored local `.env`. The expected email must be the actual account being authorized. `GOOGLE_REDIRECT_URI` may be omitted; if set, it must equal the registered URI above. An ordinary API key cannot authorize private Gmail or Drive access. Do not paste account passwords or tokens into chat.
4. Run `npm run google:connect` on this computer and open the displayed consent URL. Consent requests only `gmail.readonly` and `drive.readonly`, with offline access. The loopback callback uses PKCE and a random, expiring, single-use state. Before saving anything it verifies the granted scopes and Gmail account email.
5. Successful consent writes only ignored `.env.google` with mode `0600`. An existing file is preserved unless `--force` is explicitly supplied. Restart the local API so its environment includes this file.
6. In the Railway service's secret variables, securely set the five values saved in that file: client ID, client secret, expected account email, redirect URI and refresh token. Do not commit the file or paste its contents into chat. Restart the service after adding variables. The local callback is only for initial consent; Railway uses the refresh token without running a public OAuth endpoint.

No Google account, credentials, or live access were supplied during implementation. Installation/configuration does not mean OAuth has been verified.

## Access and runtime behavior

Only an authenticated server-owned principal explicitly granted `googleAccess: true` may invoke these tools. The root application may provide an explicit development-only operator switch; it must never grant all production members access to the club mailbox or Drive merely because the shared account can read it. Choose the member visibility policy before exposing this account through production chat.

`createGoogleClient().status()` reports `configured`, `oauthVerified`, and a sanitized status without network access. The first permitted tool request obtains or refreshes an access token, verifies both read-only scopes and the expected account, then reads the requested information. The official auth library refreshes expiring access tokens. Invalid/revoked grants return `reauthorization_required`; repeat consent and replace the Railway refresh-token secret. API denial, rate limits, unsupported files, oversized responses and partial content remain explicit. Original links are preserved; data is not copied to Supabase by this connector.

Drive search and direct-child folder listings preserve Google’s opaque pagination tokens exactly, including printable punctuation such as `~` and `!`. Tokens must contain 1–2048 printable ASCII characters with no whitespace or controls; invalid inputs are rejected before OAuth. The same rule validates provider responses, model tool arguments and chat continuation context. URLSearchParams encodes the unchanged token for the fixed Drive endpoint. A continuation page, returned cursor or `incompleteSearch` flag remains partial coverage; pagination never implies recursive folder coverage. Google documents pageToken/nextPageToken as strings, not base64, in [Drive files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list).

API reference: [Gmail message reads](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get), [Drive text exports](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export), and [Google auth library](https://docs.cloud.google.com/nodejs/docs/reference/google-auth-library/latest).

## Update agent Calendar consent and target

Set GOOGLE_CALENDAR_ID to the exact user-selected secondary/shared calendar ID; there is no primary-calendar fallback and model arguments cannot select another calendar. The user supplied Tech’s fall26 target, now configured in ignored local .env. To add access, run `npm run google:connect -- --force --calendar`. This adds `calendar.events` and `calendar.calendarlist.readonly` to the existing Gmail/Drive readonly grants. Google’s event OAuth scope covers the account’s calendars; backend Calendar tools additionally pin all reads/writes to the configured target. The Calendar API must be enabled in the OAuth client’s Cloud project.

`createCalendarClient().preflight()` verifies the expected account, granted scopes and exact target calendar-list role; writes require owner or writer. The chat application’s Calendar plugin has independent credentials and is not the unattended worker’s connector. Scope consent alone never establishes target write access. Existing hosted collector secrets are unchanged by local consent.

The update agent’s `list_calendar_events`, `read_calendar_event`, `upsert_calendar_event` and `cancel_calendar_event` tools reconcile Miro-sourced managed events. Upserts use stable source identity, provenance, exact dates/timezones, deterministic event IDs, private ownership/hash markers and conditional ETag writes. Human-modified/unmanaged events are preserved. Cancellation requires explicit evidence for an existing managed source, not missing board items. No attendees, invitations, recurrence or arbitrary event deletion are exposed. Live OAuth/ACL verification and autonomous runtime deployment status are recorded in the milestone snapshot.

## Shared chat Calendar tools

Website and Discord chat expose the same stable Calendar catalogue: list, read, create, update and soft-cancel. Wording never hides a Calendar tool or grants/denies its execution. The model interprets the current request in conversation, clarifies ambiguity and ignores instructions inside retrieved/quoted content. This semantic decision is model behavior, not a deterministic source-injection guarantee. Backend checks independently enforce trusted Google access, the configured fixed calendar, schemas, supported event types, request operation identity and fresh hidden revisions before edits/cancellation. Stateless public tool execution still cannot write. Actual attempts and canonical successful receipts inform remaining work; source text or a proposal never proves a saved change. The autonomous managed-event connector keeps its existing source ownership and evidence rules.

Explicit requests to copy dated source rows use create_calendar_events, a chat-only batch for up to50all-day entries. Clear person/date rows need no clock-time, new title approval or attendee identity lookup. The server calculates exclusive next-day ends, checks only relevant date windows with complete bounded pagination, skips exact existing title/date entries and leaves unrelated overlaps untouched. It returns row receipts and requested/created/existing/failed/unattempted counts, including partial outcomes. Google access/fixed target/idempotency checks remain mandatory; shared access failures stop later rows. A timeout or disconnected chat may not receive partial results; retry reconciles existing events.

Drive content is supplied as driveContent with original URL/fileId, up to12000characters, textTruncated and firstSheetOnly. A short source excerpt is not the entire available text; a first-sheet export is not a complete workbook. The user’s explicit source/date/year/title and skip rules carry through corrections; literal dates remain literal, blank/unassigned/TBD rows are skipped and clear independent rows proceed before reporting unresolved rows.

Calendar batches support both timed and all-day events. Use compact date/startTime/endTime/timeZone when local hours are known, or canonical start/end boundaries; never replace known clock times with descriptions or all-day entries. Compact clocks preserve local hours across DST and reject ambiguous/nonexistent times. update_calendar_events corrects up to50exact existing event IDs in place using hidden fresh revisions; Google conversions explicitly clear incompatible nested boundary fields. Narrow list_calendar_events with query and limit up to25 to obtain a series’ IDs without broad repeated scans. Per-row receipts report actual start/end/timezone and created/existing or updated/unchanged outcomes.

For bulk-edit discovery, list_calendar_events supports resultMode=identities with query and limit25. This mode omits long descriptions, location and source metadata, preserving exact event IDs, timing, status and canonical links under unchanged context bounds. Follow the actual cursor with the same query/window/mode. Default full supplies selected details for description questions or ambiguous selection; every bulk update independently performs a full fresh revision read.
