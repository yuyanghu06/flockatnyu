# Discord conversations

Flockbot responds automatically to explicit bot mentions and replies to its own messages in the currently enabled, nonblacklisted eboard and team channels and eligible descendant threads. Ordinary messages, other guilds, DMs, bot/webhook authors and blacklisted leadership channels do not trigger chat. Implementation is independent of Morpheus source code; no archive or index is added.

## Shared assistant and caller identity

`server/chat-runner.js` executes the same retrieval/answer/provider/audit lifecycle for website and Discord. The website retains its existing body validation, password authentication and NDJSON protocol. `chat-request-context.js` validates server-only Discord context containing the original request ID, guild/channel/thread, stable Discord user ID, username and server display name. Both planning and answer prompts receive it as data. Names do not grant source access, establish a linked roster identity or authorize actions. Browser-supplied identity context is ignored.

The web service resolves current member details independently before inference. It computes current member View Channel, Read Message History and send permissions with guild roles/overwrites, pending/timeout checks and private-thread membership. Owner/admin and manage-thread permissions follow Discord semantics. Current eligibility is checked again before a generated response leaves the service.

## Automatic context

Every accepted Discord request automatically loads original message text from the invoking channel or thread for the exact hour before the triggering Discord snowflake timestamp. It follows the existing live-window pagination, keeps whole records with author IDs/names and UTC timestamps in chronological order, and excludes the triggering message already present as the current request. It does not sweep other channels or include a parent channel when invoked in a thread.

The server also reads the existing Supabase `map_people` directory, selecting exactly `discord_user_id,display_name` for nonnull Discord IDs. The model receives only Discord ID/name pairs plus completeness metadata, without emails, avatars, profile UUIDs or activity data. Duplicate conflicting IDs are omitted. Both automatic contexts reach planning and answering, remain separate from the verified current actor, and cannot authorize actions or source access. Their raw data is absent from audit events and NDJSON metadata; browser bodies cannot supply them.

Recent text is capped at 2000 messages / 120000 characters and 4000 characters per complete record, with a 60-second loading budget. Directory context is capped at 1000 mappings. Missing pages, budget limits, non-text messages or source failures are explicitly marked incomplete; the assistant must disclose that limit rather than claim to have read everything. Supported image attachments are fetched separately within the same request budget as described below; embeds and other non-text payloads remain unread. No message archive or directory copy is persisted. The overall Discord request deadline is 20 minutes by default and at maximum (`DISCORD_CHAT_TIMEOUT_MS=1200000`), covering context loading, model work and final access checks. Set the same value on web and discord-events; explicit shorter overrides remain supported. The collector adapter, web bridge and Discord instance of the shared runner use this deadline. The private HTTP transport allows an additional 30 seconds, while the adapter's cancellation signal remains authoritative. Website requests use their separate `ASSISTANT_REQUEST_TIMEOUT_MS` setting; individual provider/source deadlines and cancellation guards remain independent.

Broad `read_discord_summary` scans share one five-minute deadline across catalogue discovery, sequential channel reads and any per-channel summarization. The deadline is not five minutes per channel. Exact requested team-channel summaries continue to use the existing single-window path, whose live traversal defaults to120seconds and is capped at120seconds. Individual summary model requests retain their30second deadline. Earlier caller cancellation, source/pacing bounds and shared summary content/cost limits still apply. Website `ASSISTANT_REQUEST_TIMEOUT_MS` now defaults to seven minutes (420000ms), retaining its ten-minute cap and explicit shorter overrides, to leave room around a five-minute scan for planning and the final answer. Discord's overall twenty-minute deadline is unchanged.

## Source and audience boundary

Discord uses the same shared chat runner and all website assistant adapters: live Discord reads/summaries, Google mail and Drive, Calendar, read-only Miro, map/event tools and attendance, shared memory and bug reports. Tools remain subject to their current configuration, source permissions and action/evidence checks. Calendar and configured attendance tool definitions stay visible regardless of user wording. The model interprets the current request and conversation, including informal phrasing and confirmations, and asks when actions or targets are ambiguous. A visible tool does not request an edit; ordinary questions, negation, quoted/reported source instructions and assistant suggestions do not request mutations. Calendar execution retains current Google permissions, the fixed target, argument validation, request-only writes and exact fresh revisions. Progress reports actual attempts and successful receipts rather than parser-derived authorization. Attendance service declaration/identity/date checks and map/source/team policies remain unchanged. Each successful Calendar action has its own receipt; partial failures stay visible. Calendar overlaps alone require no extra confirmation and never authorize cancelling another event. Google access uses the same explicit `SITE_GOOGLE_ENABLED=true` grant as the website. Miro remains read-only. This parity does not turn a Discord ID or display name into a linked roster identity, original source evidence or permission to bypass a write guard.

The server constructs the principal with the full configured shared-source UUID allowlist for these adapters. It separately puts the audience-safe Discord UUID subset in `principal.liveDiscord.allowedSourceIds`; every Discord read from this transport requires a valid nonempty bounded subset and intersects it with the full allowlist before catalogue or source access. Missing/malformed subsets fail closed. Other adapters retain their existing source gates. The conversation profile binds both lists, the Google grant and exact invoking destination, so a revocation invalidates retained history and prevents publication after the final authorization check.

`chat-access.js` intersects the server source UUID allowlist with the currently enabled eboard/team catalogue and current exclusion/ancestry policy. The invoking destination must be registered and eligible; a disabled parent cannot be bypassed through a thread. Eboard source channels/public threads must have equivalent View Channel and Read Message History overwrite rules to the destination; privately restricted threads are available only as their own destination. Team sources are limited to the exact invoking destination and its registered parent for thread readiness. Equal audience permissions do not add sibling team channels. Missing permission metadata narrows to the invoking channel and eligible parent. All source tools retain their own final policy checks. Source mapping/names/ancestry, policy and invoking-destination changes invalidate transient conversation profiles.

## Services and configuration

The existing `discord-events` service owns the only Gateway connection. A bounded, detached chat hook handles native message events; model latency does not delay pending-input ingestion/checkpoints. Chat-generated create/update messages are excluded from autonomous input collection while chat is active. Other collector behavior is preserved.

The collector calls the web service's `/internal/discord/authorize` and `/internal/discord/chat` endpoints. They require a separate private bearer secret, reject browser Origin headers, and cannot be authorized by the site password/cookie. Body-supplied principals/actor labels are rejected; the web service constructs them, including source lists and the Google grant. No secret belongs in browser variables, committed files or model context.

Set private Railway variables on both web and discord-events:

- `DISCORD_CHAT_ENABLED=true`
- `DISCORD_CHAT_BRIDGE_SECRET`: the same private random value of at least 32 characters.

On discord-events additionally set `DISCORD_CHAT_API_ORIGIN` to the web service's verified Railway private hostname and listening port, such as `http://web.railway.internal:3000`. Full 20-minute requests require this private route: Railway public HTTP has a 15-minute request maximum and a 5-minute idle limit ([Railway limits](https://docs.railway.com/networking/public-networking/specs-and-limits)). Public HTTPS origins remain supported for shorter requests. Plain HTTP is accepted only for an exact single-service `railway.internal` hostname with an explicit valid port and root path; credentials, nonroot paths, query strings, fragments and arbitrary HTTP hosts are rejected. Private requests use native Node HTTP with the composed request deadline/cancellation signal and the existing 250 KB response cap, avoiding fetch's separate headers timeout. The shared secret and all bridge authorization checks remain required. Deploy updated source to both web and discord-events; changing variables or restarting the old collector image leaves the earlier timeout cap and HTTP rejection in place. The web listener must accept Railway private IPv6 traffic as well as public traffic (`HOST=::`); use its actual listening `PORT` in the private origin. Existing bot, guild, shared-source and service settings remain authoritative. Chat defaults disabled. The web service needs its existing Discord read configuration and source allowlist; enabling chat does not expand them.

No slash command is registered or handled. A normal `@Flockbot` mention invokes the assistant automatically; a bare mention uses the recent conversation as its question context. Existing unrelated application commands remain untouched. Bot send/thread permissions must exist.

## Limits, history and failures

Default limits are 3 concurrent transport requests, 1 per member and 20 requests/member/hour. Slots are reserved before authorization or other network work; overload returns without further allocation. Mentions show bounded typing pulses. Requests allow 8000 characters, and generated output is capped at 8000 then split into at most 2000-character messages. Every delivery suppresses automatic mentions and preserves the actual channel/thread. Missing reply targets do not fall back to channel announcements.

Histories are RAM-only, expire after 30 minutes, and are isolated by member, destination/thread and current source profile. Default maximum 100 histories; conversation count/characters/UTF8 bytes retain the shared API bounds. No tool-result history is retained. Default deduplication lasts 1 hour with 2000 entries; active requests also remain deduplicated independently of cache eviction. Histories and replay protection reset on process restart. Automatic source contexts are rebuilt for every request and are not stored in conversation history. There is no durable job queue or guaranteed exactly-once delivery across crashes. Partial or ambiguous sends are not automatically replayed. Website and Discord histories remain separate.

Private seven-day model audit still records returned model text/usage and content-free run/tool outcomes; it never records request prompts, actor-context objects, interaction tokens or raw tool responses. Existing source retention rules remain unchanged.

An earlier assistant claim that editing was unavailable is historical; no attempted write is not a permission denial. Attachment conversations retain the existing multimodal planning path. Native result context is bounded and omitted content is explicitly incomplete; successful receipts survive. This does not change source access or force a mutation.

Source-to-Calendar copies can create up to50requested all-day rows in one create_calendar_events tool call, preserving per-item receipts and partial counts under the same website/Discord catalogue. Clear corrections/follow-ups retain the original scope and naming/date/skip rules, without new permission loops; blank or uncertain rows do not block clear rows. driveContent supplies up to12000characters separately from citation excerpts and keeps first-sheet/truncation limits explicit.

Shared chat behavior preserves requested times, dates, timezone, scope and exclusions across follow-ups, uses compatible tools and completes or repairs authorized work before reporting actual blockers. Timed and all-day creation batches and exact-ID bulk correction return saved timing receipts. Final replies summarize relevant outcomes with a few useful links; discovery candidates are not a source list to append. The website now renders answer inline citations without an automatic retrieved-source footer; Discord continues to send the generated answer only.

For an @bot reply, the web service independently fetches the exact triggering message using its approved author, then rereads its direct same-channel/guild reply target. This works beyond the previous-hour window and never follows chains or accepts forwarded/embedded reference content. repliedMessage is a separately validated immutable context block with whole text up to10000characters, canonical URL and allowlisted author/timestamps. The text block omits non-text bodies; supported attachments can be read through the separate image context described below. Oversize/missing/denied targets are explicitly partial or unavailable without blocking unrelated chat. Existing source/audience/policy checks are reverified after reads.

Both model phases identify that target as the current “this/that” referent and may use its facts to fulfill the current authorized user request. Source text never grants instructions or new access, and its author never replaces the approved speaker or supplies provider-map identity receipts. Hour-window coverage remains independent. Reply content remains transient and is absent from client metadata and operational audit/log payloads. Collector transport/schema and website-browser source context are unchanged.

## Image context

The web service reads native PNG, JPEG and WebP attachments from the freshly verified invoking message, its exact direct reply target, and a bounded set of messages in the authorized previous-hour context. Priority is invoking message, reply target, then newest recent messages; duplicate attachment IDs are read once. The direct reply can be older than one hour. Images found by subsequent source-tool searches are outside this automatic context. GIF, SVG, videos, stickers, embeds and external image links remain unread, with relevant limitations disclosed. If the direct reply cannot be retrieved, image context is conservatively withheld for that request while text chat can continue.

Image downloads accept only native Discord CDN attachment URLs bound to the exact channel and attachment IDs returned by authorized live reads. Fresh message reads supply current signed attachment URLs ([Discord documentation](https://github.com/discord/discord-api-docs/blob/main/developers/reference.mdx)). Downloads reject redirects, foreign hosts and mismatched paths, omit bot authorization, and enforce MIME/signature, cancellation and streamed byte bounds. At most four images, 5 MiB each and 10 MiB total, enter a request; candidate processing is bounded to forty. Current source policy and destination access are checked again after downloads, and a revoked source cannot contribute image bytes to inference.

The bridge attaches successfully read images to an ephemeral clone of the current user message, preserving its question exactly. The existing multimodal planning and answer phases receive the image content. Separately validated image metadata associates each image with its origin message and records partial, unsupported or unavailable results. Image text, pixels and filenames are untrusted reference data: they cannot request actions, widen permissions or establish participant/provider identities. Only the current user request grants action intent, and existing source/identity write gates still apply.

Image bytes and signed CDN URLs do not enter system prompts, returned chat metadata, transport histories or operational logs. The private audit retains its existing authorized model outputs and content-free outcomes, without raw image inputs. Bridge request bodies still reject caller-supplied attachments. This is a web-service capability; the collector transport and autonomous planner are unchanged. Local acceptance and the actual deployment state are recorded in the rolling milestone.
