# Miro daily sync and assistant reads

M27 adds a dedicated native Node worker, a new `public.miro_boards` table, and
read-only assistant tools. The club uses Miro Free and ordinary shapes, text,
cards and sticky notes. Original board/API object data is retained; calendar
interpretation, screenshots, external document bodies and binary assets are not
generated by the sync. Current hosted rollout and missing authorization belong
in `milestones/milestone.md` and `evidence/m27-miro-sync/`.

## Database

Original migration `202610150012_miro_board_sync.sql` is applied and immutable.
Migration014 simplifies the table to12columns and renames `snapshot` to `data`.
Apply only new migrations to the existing project; never replay the directory.
Current hosted version receipts belong in the rolling milestone and evidence.

`miro_boards` holds one current complete snapshot per board: original board
metadata, hydrated items, geometry/style/rich text, connectors, groups, tags and
memberships, stored in the `data` JSONB object. Its arrays hold individual items,
connectors, groups and tags, with relationship maps and capture/coverage metadata.
The other11columns retain board/source identity, team/enabled configuration,
config revisions, last success, status/error and exclusive worker lease. Title,
URL and counts are derived rather than duplicated in columns. Successful replacement
also removes objects deleted since the previous capture. No accumulating daily
snapshot history is retained.

Each capture acquires and renews a lease. A single guarded RPC publishes the
complete result atomically; partial reads, ambiguous pagination, limits, edits
during capture, disabled sources or stale leases cannot overwrite the last good
snapshot. Board modifiedAt is checked before/after; this is not a transactional
snapshot of Miro itself. Access failures retain old data privately but block its
cached reader. The worker does not follow card links or pagination URLs.

The table forces RLS and is service-role only. Registering a board creates a Miro
knowledge source. Shared reads require the source to be active, the board enabled
and its source ID present in the trusted backend allowlist. Migration016 removes
per-person membership tables; no member accounts or grants are required. Token
visibility alone does not expand the backend allowlist.

## Configure and run

Server-only variables:

- `MIRO_ACCESS_TOKEN`: the authorized Miro app's **non-expiring** token with
  `boards:read`. No Miro writes are needed. Expiring-token OAuth refresh is not
  implemented, so a one-hour access token cannot support unattended daily sync.
- `MIRO_BOARD_IDS`: comma-separated exact board IDs or board URLs. No token-wide
  board discovery occurs. `MIRO_TEAM_ID` is an optional additional restriction.
- `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`: existing trusted database runtime
  credentials. Never expose them in browser bundles or chat.
- `MIRO_SYNC_ENABLED=true` enables sync; default false explicitly reports disabled.
  This switch does not grant assistant access or disable authorized live reads.

Use the normal Miro developer app setup, install it into the club team and select
non-expiring authorization when creating it. Store real credentials only in an
ignored local environment file or Railway variables. See the official
[authorization choices](https://developers.miro.com/reference/authorization-flow-for-expiring-tokens)
and [REST setup](https://developers.miro.com/docs/rest-api-build-your-first-hello-world-app).

Commands load the local ignored `.env`:

```sh
npm run miro:preflight
npm run miro:sync
npm run worker:miro
npm run test:miro
npm run deploy:miro:prepare
```

Preflight reads board metadata without database writes. Manual sync bypasses the
hour gate, but still requires enabled configuration. The scheduled command runs
at local hour06 in America/New_York. Railway uses UTC, so cron `0 10,11 * * *`
checks both seasonal candidates and the worker skips the other hour; actual sync
is once per day across DST. Service restart policy is NEVER, with no HTTP health
check. Every invocation exits when complete. A future observed cron run is
separate evidence from configured cron and successful initial deployment.

Default bounds:20 minutes,32MiB downloaded/snapshot,20000 objects per collection,
bounded retries and request/page limits. Hitting a bound fails that board rather
than publishing a truncated snapshot. Errors log safe codes/counts only. The
deployment preparer copies only `server/miro/*.js`, a minimal ESM manifest and the
dedicated Dockerfile, excluding all unrelated application changes and secrets.

## Direct assistant API access

The normal Hono runtime creates `miroTools`. The provider's tool planning can call:

- `list_miro_boards`: explicitly authorized configured board catalogue.
- `read_miro_board`: live frame overview or paginated original objects in a board
  or frame, including hydrated text and geometry.
- `read_miro_item`: live original object plus immediate parent; large objects are
  JSON fragments recoverable through `nextOffset`.
- `read_miro_relationships`: live connectors, groups, tags or memberships.

Definitions appear in protected `GET /api/tools`; protected
`POST /api/tools/<name>` invokes the same adapter. Chat receives original object
layout through bounded `boardContext`, alongside original source URLs. Miro can
use four dependent planning rounds within the existing four-tool-call budget;
other connectors retain their two-round behavior. No model credentials are sent
to Miro, and the model never receives Miro/Supabase credentials.

Configure the same token/board allowlist in the API runtime. Once the actual board
is registered, add its source ID to the shared `ASSISTANT_ALLOWED_SOURCE_IDS`
backend setting (`DEV_ALLOWED_SOURCE_IDS` remains a compatibility alias). No
per-person grants are needed. The API still controls its trusted request context;
no browser header or model argument can change the source allowlist. Direct tools
read live Miro and never fall back to cached data after access denial.

Model instructions distinguish calendar cells/headings/legends from inferred
event dates and card due dates. They disclose bounded pages/frames/fragments and
ignore instructions embedded in board content. No zero-context-loss or perfect
visual-equivalence claim is made. Native table cells are unavailable through the
REST API. Mixed pages retain their original table metadata and supported objects,
with explicit metadata-only itemCoverage, partial status and unsupportedTypes.
Unknown per-item content requests disclose the gap without probing detail endpoints.
Supported access failures still discard the whole page.
